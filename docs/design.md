# 設計取捨

第一版是 2026-09 用一個人的 8–9 月資料手跑出來的。這裡記為什麼長這樣，以及被否決的方案。

## 為什麼不全自動

時數不是量測值。三層估法裡只有會議時數是硬的，commit 跨度偏保守，剩餘歸屬是推估。
實測 206.5h 裡 131h 整列有時間戳、48h 部分有、27h 只有任務日期範圍。
所以草稿一定給人改，而且每列帶「依據」欄，被問時答得出來。

每週跑會比回推一個月準：五天內的殘餘時數人憑記憶就能改。

## 週 TTL：卡鐘實際工時，不是 40

| 方案 | 結果 |
|---|---|
| 固定 40h | 請假週灌水；實測有一週只有 16h |
| 名目 8h/日 − 請假 | 加班全部消失 |
| 卡鐘實際工時 | 採用；沒卡鐘才退回 40 並標未驗證 |

遠端辦公、忘刷卡這類假別的殼底下人在工作，算整天；病假、特休不進表。

## 分類：帳本優先，關鍵字其次，最後問人

關鍵字只能給第一次猜測。「事故後優先處理的都算 X」這種因果規則被否決：
它會把不相關的東西一起掃進去，而且會計問起來答不出邊界。
改成工單層級的帳本：一個工單一個決定，人拍板，之後沿用。同一工單每週答案一致。

會議、課程、workshop 用一個預設分類加例外清單，因為它們很少有工單。

## 標題：兩欄

給主管與會計看的標題要短、沒有術語、沒有內部代號。
消融法：把「系統、機制、建置、後端、主站」這類拿掉不改變意思的詞刪掉，
剩下「誰、做什麼、為了哪個活動」。技術描述與工單編號留在草稿的第二欄，不進輸出。

「主站」這種詞要避開：對另一條產品線的人來說它暗示「不是我們的」。

## 每週 4–6 列

同工單、同產品線、同類會議合併。合併列的第二欄列出原始工單編號，追得回去。

## 設定各人自管

團隊可以給 template，但 `~/.config/timesheet/` 是每個人自己的。
skill 維護 `rules.yaml` 與 `ledger.yaml`，人只監督：改動列出來，點頭才寫。

## 不放進這個 repo 的東西

公司或團隊專屬的關鍵字、追蹤系統工具名、Sheet id，都在各人的 config。
這個 repo 只有流程、格式與範例。
